# PLM 接口化与「去 3100」演进方案（讨论稿）

> 版本 v1.0 ｜ 2026-11-11 ｜ 状态：**讨论中，未执行**
> 背景：库存已改为调用 PLM 既有 `ERPService.GetStockSearchData`（v1.44/v1.45），
> 由此引出两个方向性选择：① 查询全部走 PLM，3100 只做查重/校验；② 脚本全部搬到 PLM，完全脱离 3100。
> 本文记录讨论结论、可行性与执行前置条件，供后期决策。

---

## 一、现状：各项能力由谁承担

| 能力 | 当前实现 | 能否由 PLM 接口替代 | 说明 |
|---|---|---|---|
| 库存 | PLM `ERPService.GetStockSearchData` | ✅ **已替代** | v1.44 起浏览器内直调，复用登录会话 |
| 物料基础数据（编码/名称/规格/小类） | 3100 索引 `data/materials.ndjson`（约 2.3 万条） | ⚠️ 能查，性能待验证 | PLM 有 PSE 数据服务，但批量/分页能力未知 |
| 同小类历史规格联想 | 3130 `/api/new-material/spec-suggest` | ⚠️ 可查，排序要自算 | 需要按输入前缀过滤 + 统计 |
| 相似型号排序（接近度） | 3130 `/api/new-material/similar-models` | ❌ | PLM 不提供相似度算法 |
| 名称同义词 / 标准叫法 | 3100 `name-synonyms.json` | ❌ | PLM 无此词表 |
| 书写规则校验 | 3100 `material-rules.js` | ❌ | PLM 无此规则 |
| 查重（一物多号） | 3100 索引 + 相似度 | ❌ | 需全量索引 + 算法 |
| 规则热更新 | 3100（改 JSON 即生效） | ❌ | PLM 侧改配置需发版 |

**核心结论**：PLM 提供的是**行数据**，不提供**算法**（相似度、同义词、规则）。因此「全部查询走 PLM」只能覆盖前两行。

---

## 二、方案 A：查询走 PLM，3100 只做查重 / 校验

**做法**：物料、库存、规格候选改调 PLM 服务；3100 保留规则引擎 + 索引 + 查重。

| 维度 | 评价 |
|---|---|
| 数据一致性 | ✅ 单一数据源，避免「PLM 有、3100 没有」 |
| 实时性 | ✅ 不依赖快照刷新 |
| 性能 | ⚠️ 联想需按小类拉数据，单次几十~几千行；内存索引的几十毫秒优势会消失 |
| 算法能力 | ⚠️ 相似度、统计排序仍需浏览器或 3100 计算 |
| 改造量 | 中：`snapshot.js` 的 ERP 直连改为 PLM 取数，对外接口形状不变 |
| 资产保护 | ✅ 规则/词表仍在自有服务器 |

**适合**：以 PLM 为唯一数据源、但仍希望保留自有算法与规则的场景。

---

## 三、方案 B：脚本全部搬到 PLM，完全脱离 3100

### B1. 放在浏览器（纯前端）

| 维度 | 评价 |
|---|---|
| 可行性 | 单小类几百条可行；**全量 2.3 万条不可行**（首屏体积 + 每次按键比对） |
| 性能 | 每次联想网络往返 + 前端排序 |
| 数据新鲜度 | ✅ 每次实时查 |
| 维护 | 规则改动需重新发布 JS |
| 规则暴露 | 规则代码随 JS 下发，可被读取（与现状相同） |

### B2. 放进 PLM 服务端（自定义 DLL / 插件）

| 维度 | 评价 |
|---|---|
| 可行性 | PLM 支持注册自定义服务（参见 `TSDC\ERP\Config\ERPService.service`） |
| **资产风险** | **软件方可登录 PLM 服务器** → 核心算法等于交出，与「源码泄露、资产仍在手里」的目标冲突 |
| 升级风险 | PLM 打补丁/升级会覆盖 `Bin`、`Config`，每次需重新部署 |
| 排障权限 | IIS 日志、服务进程在对方手里，问题定位受制于人 |
| 交付形态 | 变成寄生在 PLM 上的插件，难以单独交付/复用/定价 |

**结论**：除非客户强制「只能有一台服务器」，否则不建议。

---

## 四、方案对比

| 维度 | 现状（3100 + 3130 + 直连 ERP） | 方案 A（查询走 PLM） | 方案 B（完全脱离） |
|---|---|---|---|
| 数据一致性 | 中（快照可能滞后） | 高 | 高 |
| 性能 | 高（内存索引） | 中 | 低~中 |
| 算法能力 | 完整 | 完整 | 受限/需重写 |
| 资产保护 | 强 | 强 | **弱（B2）/一般（B1）** |
| 升级耦合 | 低 | 低 | **高** |
| 排障自主性 | 强 | 强 | 弱 |
| 改造量 | — | 中 | 大 |
| 运维成本 | 一台服务器 | 一台服务器 | 零服务器（但风险转移） |

## 五、建议路线（分三步，不急于脱离）

| 阶段 | 做什么 | 收益 | 风险 |
|---|---|---|---|
| **第 1 步（已完成）** | 库存走 PLM `ERPService` | 去掉一条直连，口径统一 | 低 |
| **第 2 步** | 3100 物料索引**改为从 PLM 同步**（定时/按需），不再直连 ERP | 数据来源统一到 PLM，索引仍在自有服务器 | 中：需确认 PLM 取数接口的分页与性能 |
| **第 3 步（可选）** | 把「轻规则」（长度/类型/空格/括号）下放浏览器，3100 保留重规则 + 查重 + 相似度 | 减少网络往返，弱网体验更好 | 中：规则分散到两处，需同步维护 |

**关键判断**：「查询走 PLM」≠「逻辑走 PLM」。数据以 PLM 为准可以做到，同时规则与算法留在自有服务器——这是「数据统一 + 资产可控」的平衡点。

## 六、完全脱离前必须回答的四个问题

| # | 问题 | 影响 |
|---|---|---|
| 1 | 单小类最多多少条？全库多少条？ | 决定能否在浏览器算相似度 |
| 2 | 联想延迟能接受多少毫秒？（现为几十毫秒） | 决定是否需要保留本地索引 |
| 3 | PLM 服务器升级/重启/故障谁负责？能否登录排查？ | 决定故障恢复时效 |
| 4 | 这套能力是否要复用到其他客户/其他 PLM？ | 决定逻辑是否必须留在自己手里 |

## 七、执行清单（决策后使用）

### 第 2 步：索引改为从 PLM 同步

- [ ] 确认 PLM 取数接口：物料列表（按小类 / 按编码 / 增量）
- [ ] 确认分页与单次上限（`Limit`、`StartRow`）
- [ ] 设计增量策略：按修改时间 / 按小类全量覆盖
- [ ] 改造 `src/snapshot.js`：ERP 直连 → PLM 服务
- [ ] 保留降级：PLM 不可用时继续用旧快照（不回落直连）
- [ ] 校验口径：数量、字段映射（编码/名称/规格/小类/单位）
- [ ] 回归：`verify-plm-plugin.mjs` + 看板冒烟

**验收**：`/api/new-material/spec-suggest` 返回与 PLM 一致；索引刷新后差异为 0。

### 第 3 步：轻规则下放（可选）

- [ ] 列出可下放的规则（长度、类型白名单、空格、括号、全角）
- [ ] 浏览器端实现并与 3100 结果比对（一致性测试）
- [ ] 保留 3100 兜底：前端规则失败时仍可请求服务端

**验收**：同一输入下，前端与 3100 判定结果 100% 一致。

## 八、风险与回退

| 风险 | 应对 |
|---|---|
| PLM 服务不稳定 | 保留本地索引与快照，PLM 失败时降级 |
| PLM 升级导致接口变更 | 数据适配层单独封装（`plm-inventory.js` 模式），只改一层 |
| 规则分散难维护 | 第 3 步仅下放「无状态轻规则」，重规则仍集中 |
| 账号/权限变更 | 服务账号独立、只读、纳入变更清单 |

**回退**：各阶段均保留「关开关回到上一步」的能力（`inventorySource`、`allowDirectErp` 已是此模式）。
