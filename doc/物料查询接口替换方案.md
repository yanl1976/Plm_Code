# 物料查询接口替换方案（PLM 标准接口）

> 建立：2026-11-14　状态：**待开发**
> 目标：插件在 PLM 侧录入物料时，用 **PLM 标准查询接口**获取已有物料，替代/补充当前的 ERP 直连查询。
>
> **硬约束（不得违反）**
>
> 1. 插件**只能调用 PLM 标准接口**（`HoteamUI.DataService`），**不得直连数据库**
> 2. 数据库连接仅用于开发期分析，运行时一律走接口
> 3. 只处理编码前缀 **`10` / `11` / `12`** 的物料（与系统设置 `materialPrefix.include` 一致）
> 4. 只允许引用 **`STATEID = 'Using'`（启用）** 的物料，停用/废弃/待审核一律排除
> 5. 禁止访问生产库 `198.168.6.15`，一切以 `.env` 为准

---

## 一、背景

当前插件的「查已存在物料」能力来自 **ERP 直连数据库**（`src/plm-index.js` 读 `materials.ndjson`，由 `extract.js` 从 `T_BD_MATERIAL` 全量导出）。

存在三个问题：

| 问题 | 说明 |
|---|---|
| 数据滞后 | 快照按天/按次更新，ERP 刚建的物料查不到 |
| 依赖 ERP 库 | 需要数据库账号，网络/权限受限 |
| 与工程源头脱节 | 物料实际在 **PLM 创建**，ERP 是下游同步 |

插件部署在 PLM 页面内，**天然具备 PLM 登录态**，用 PLM 自己的查询接口最合适。

---

## 二、实测结论（2026-11-14，开发期用数据库核对）

> 以下数据用 `.env` 指向的测试实例（`198.168.6.26`）核对，**仅用于确认数据形态，不作为运行时依赖**。

### 2.1 数据规模

| 项 | 数值 |
|---|---:|
| PLM `PSEITEM` 总行数 | 116,035 |
| 物料数（`EUID` 去重） | 114,752 |
| 最新版行数（`EID = ELASTINSERT`） | 114,747 |
| **PLM 中 10/11/12 编码数** | **55,515** |
| **其中 `STATEID='Using'`（可引用）** | **15,141** |
| ERP 编码数（10/11/12，去重） | 23,059 |

### 2.2 覆盖率

```
PLM 启用（15,141） ∩ ERP（23,059） = 15,087
仅 ERP  = 7,972
仅 PLM  = 54
覆盖率 = 15,087 / 23,059 ≈ 65.7%
```

**关键洞察**：PLM 启用的物料中 **99.6% ERP 也有**，PLM 几乎不提供 ERP 之外的物料。

因此本方案定位不是「替代 ERP」，而是：

- **主力源**：PLM（数据最新、与工程源头一致）
- **兜底源**：ERP 快照（补齐 PLM 缺失的 34%）

### 2.3 物料状态（`STATEID`，界面「使用状态」）

| 值 | 界面 | 条数（10/11/12 最新版） | 可否引用 |
|---|---|---:|---|
| `Using` | 启用 | **15,141** | ✅ 唯一可用 |
| `Stop` | 停用 | 40,163 | ❌ |
| `WaitingAudit` | 待审核 | 211 | ❌ |
| `GiveUp` | 废弃 | 0（当前无数据） | ❌ |

> 代码依据：`InforCenterUsingState.lifestate` 定义四种；`PSEItemDic.dic` 里有「**不允许添加停用或废弃的零组件**」的提示文案，与业务规则一致。

**72.7% 的物料处于不可引用状态**，插件必须严格按 `STATEID` 过滤。

### 2.4 字段可用性

| PLM 字段 | 含义 | 填充率 | 对应 ERP |
|---|---|---:|---|
| `ECODE` | 编码 | — | `FNUMBER` |
| `ENAME` | 名称 | — | `FNAME` |
| `GGXH` | 规格型号 | **92.3%** | `FSPECIFICATION` |
| `ZYCS` | 主要参数 | **6.9%** ⚠️ | `F_ZXCV_ZYCS` |
| `UNIT` | 单位（是 ID，不是名称） | — | 单位名称 |
| `STATEID` | 使用状态 | — | 无对应 |

**`ZYCS` 几乎为空**，主要参数不能依赖 PLM，仍需 ERP 或人工填写。

### 2.5 编码格式

| 格式 | 条数 | 占比 |
|---|---:|---:|
| 6 位数字 + 后续 | 56,635 | 49.4% |
| 其他（`0`、`00001`、`205S10`） | 58,106 | 50.6% |

**只有一半是标准「6 位小类 + 序号」**，推小类不能只靠 `slice(0,6)`，需回退到 ERP 的 `SUBPREFIX`。

### 2.6 已知数据问题

```
PLM 状态为「停用」但 ERP 仍存在：493 条
```

需要业务决定以哪边为准，**不在本期开发范围内**，但要在差异报告中列出。

## 三、接口规格

### 3.1 调用方式（插件内，标准接口）

```js
window.HoteamUI.DataService.AsyncCall({
  serviceuri: 'InforCenter.Common.ObjectService.CommonGetObjectDataByFilter',
  paras: {
    para: {
      Data: JSON.stringify({
        PSEITEM: {
          FilterInfo: [],
          FilterString: "ECODE = '10010100271' AND STATEID = 'Using'",
          OrderbyString: ''
        }
      })
    }
  },
  callback: function (raw) {
    // raw 可能是字符串或对象，需逐层剥壳
    // 结构：{ PSEITEM: [ { EID, ECODE, ENAME, GGXH, ZYCS, UNIT, STATEID, ... } ] }
  },
  errorCallback: function () { /* 降级到 ERP 查询 */ },
  showErrorMessage: false
})
```

### 3.2 字段映射

| PLM 返回 | 内部字段 | 用途 |
|---|---|---|
| `ECODE` | `fNumber` | 编码 |
| `ENAME` | `fName` | 名称 |
| `GGXH` | `fSpec` | 规格 |
| `ZYCS` | `zycs` | 主要参数（可能为空） |
| `UNIT` | `unit` | 需转名称（见下方「待确认」） |
| `STATEID` | `state` | 状态判定 |

### 3.3 待验证（阶段 0 必须确认）

| # | 待确认 | 不通过的应对 |
|---|---|---|
| 1 | `FilterString` 是否支持 `STATEID` 条件 | 查询后在插件侧 `filter(r => r.STATEID === 'Using')` |
| 2 | 返回是否自动只含最新版（`EID = ELASTINSERT`） | 客户端按 `ECODE` 去重，保留 `UPDATETIME` 最新的一条 |
| 3 | 返回字段是否包含 `STATEID`（视图只暴露 40 列，表有 50 列） | 若不含，改用 PLM 列表接口或 `PSEITEMINFOVIEW` 相关服务 |
| 4 | `UNIT`（数字 ID）如何转名称 | 查 PLM 单位字典接口，或复用一个常量映射表 |
| 5 | 单次查询耗时 | 超过 1s 则加防抖 + 缓存 |

## 四、开发计划（5 个阶段，可独立验收）

### 阶段 0：接口能力摸底（0.5 天）

| 项 | 内容 |
|---|---|
| **目标** | 确认接口能查什么、返回什么，**不改任何业务逻辑** |
| **做法** | 插件里加一个临时调试入口（`window.__plmItemProbe('10010100271')`），结果打印到 Console |
| **产出** | ① 一条物料的完整返回 JSON ② 字段清单 ③ 耗时 |
| **验收** | 能拿到 `ECODE / ENAME / GGXH / STATEID`；能确认 `FilterString` 是否支持状态过滤 |
| **风险** | 接口不支持状态过滤 → 改为客户端过滤（不影响后续阶段） |

### 阶段 1：只读并行对比（1 天）

| 项 | 内容 |
|---|---|
| **目标** | 插件同时查 PLM 和 ERP，**只在 Console 输出对比，不弹提示、不改流程** |
| **做法** | 新增 `plmQueryItem(code)`；在现有查重触发点旁挂一个旁路调用 |
| **产出** | 20 条真实录入的对比日志：`编码 / PLM状态 / PLM有规格 / ERP有 / 是否一致` |
| **验收** | ① 一致率 ≥95%（实测期望 96%+）② 平均耗时 <800ms ③ 无 JS 报错 |
| **不通过** | 若一致率低或耗时高，先排查字段映射与去重逻辑，再决定是否进入阶段 2 |

### 阶段 2：接入重复校验（1 天）

| 项 | 内容 |
|---|---|
| **目标** | 新建物料时用 PLM 结果做「疑似重复」提示 |
| **规则** | 见下表 |
| **产出** | 提示文案 + 开关（`blocks.dupPlm`，默认开） |
| **验收** | 造 4 组数据各测一遍，提示正确 |

| PLM 查询结果 | 提示 | 阻断 |
|---|---|---|
| 命中 + `Using` + 规格相同 | 「PLM 已存在同规格物料，请直接引用」 | ✅ 阻断 |
| 命中 + `Using` + 规格不同 | 「PLM 已有该编码，规格是 XXX，请确认」 | ⚠️ 提示 |
| 命中 + `Stop`/`GiveUp` | 「该编码在 PLM 已停用/废弃，禁止引用」 | ✅ 阻断 |
| 命中 + `WaitingAudit` | 「该编码在 PLM 待审核，请先完成审批」 | ⚠️ 提示 |
| 未命中 | 走 ERP 快照查重（现有逻辑） | — |

### 阶段 3：PLM 快照与差异（1.5 天）

| 项 | 内容 |
|---|---|
| **目标** | 3100 定期生成 PLM 快照，输出与 ERP 的差异清单 |
| **做法** | 新增 `src/plm-snapshot.js`；**通过 PLM 接口拉取**（不直连库），需 `.env` 补 `PLM_BASE` 等 |
| **产出** | `data/materials-plm.ndjson` + `data/plm-erp-diff.json` |
| **验收** | ① 快照条数接近 15,141（可引用物料）② 差异三类计数正确 ③ 可重复执行 |

> 若阶段 0 发现接口无法批量拉取（只支持单条），则**跳过阶段 3**，改为「插件按需查询 + 3100 只存结果」。

### 阶段 4：回归与灰度（0.5 天）

| 项 | 内容 |
|---|---|
| **目标** | 全量回归 + 小范围试用 |
| **做法** | `npm run verify:plm`（84 项）+ 人工录入 10 条 |
| **验收** | ① 回归全绿 ② 10 条录入无异常 ③ 阻断开关可正常关闭 |

**合计：约 4.5 人天**

## 五、验收标准（每阶段通用）

| 项 | 标准 |
|---|---|
| 接口合规 | 只用 `HoteamUI.DataService`，无任何 `fetch` 直连数据库 |
| 状态正确 | 非 `Using` 的物料**绝不进入可用候选** |
| 范围正确 | 只处理 `10/11/12` 开头的编码 |
| 降级可用 | PLM 接口超时/报错时，自动回退到 ERP 快照，不阻塞录入 |
| 性能 | 单次查询 <800ms；连续输入有防抖（≥300ms） |
| 可关闭 | 新增能力都有开关，出问题能一键关掉 |

## 六、风险与应对

| 风险 | 概率 | 应对 |
|---|---|---|
| 接口不支持 `STATEID` 过滤 | 中 | 客户端过滤，代价是多返回数据 |
| 接口只返回已发布对象 | 中 | 那反而简单，但仍需确认 `STATEID` 字段存在 |
| 返回含历史版本 | 中 | 按 `ECODE` 去重，取 `UPDATETIME` 最新 |
| `UNIT` 是 ID 无法显示 | 高 | 阶段 0 确认；不行就沿用 ERP 的单位名称 |
| `ZYCS` 基本为空 | **确定** | 主要参数不依赖 PLM，保持 ERP 或人工填 |
| 覆盖率仅 65.7% | **确定** | 必须保留 ERP 兜底，不能单源 |
