## 二、三条主链路

### 链路 A：录入即时校验（最高频，毫秒级）

```
用户按键
   │
   ├─► 名称框 ─► /api/plm/check (3100) 或 /api/new-material/validate (3130)
   │                │
   │                ▼
   │           checkMaterial(name, spec, sub, ecode)
   │                │
   │                ├─► checkName()  ─┐
   │                └─► checkSpec()  ─┤
   │                                  ▼
   │                        合并 errors / warnings / suggestion
   │                                  │
   │                                  ▼
   │                        插件弹窗 + 状态行 / 看板校验区
   │
   └─► 规格框 ─► /api/plm/spec-complete  → 当前段 + 取值候选（Tab 采用）
                 /api/plm/suggest(field=spec) → 整条存量写法（点击采用）
```

### 链路 B：快照同步（插件拉 PLM → 合并 → 供全局使用）

```
PLM 页面控制台 __plmSync.start()
   │
   ├─► GET  /api/plm/snapshot/plan      取上次位点与待同步小类
   ├─► 逐小类查 PLM 平台接口
   ├─► POST /api/plm/snapshot/upload    分批上报（每小类一批，按 FNUMBER 去重）
   ├─► POST /api/plm/snapshot/merge     合并写 materials-merged.ndjson
   │       │
   │       └─► loadIndex({force:true})  重建内存索引（23,406 条 → 200 小类）
   │
   └─► 看板「查重快照：23,406 条 · N 天前」= 该文件行数 + mtime
```

### 链路 C：批处理（离线，分钟级）

```
node src/cli.js extract ──► 连 PLM/ERP 拉物料 ──► data/materials.ndjson
                                │
                                ▼
node src/cli.js dedup  ──► 签名聚类 ──► dedup-exact/sep/sameNumber.json
                                │         + name-sub-index.json（名称→小类）
                                ▼
node src/cli.js validate ──► 黄金样例 26 条 + 格式契约 + 覆盖率 ──► 报告 PASS/FAIL
```

## 三、录入校验的规则链（checkMaterial 内部真实顺序）

```
                       ┌──────────────────────────────────────┐
                       │ checkMaterial(name, spec, sub, ecode)│
                       └───────────────┬──────────────────────┘
                                       │
        ┌──────────────────────────────┴──────────────────────────────┐
        ▼                                                             ▼
┌───────────────────┐                                        ┌───────────────────┐
│    checkName      │                                        │    checkSpec      │
│  （5 道，按序）    │                                        │  （3 道，按序）    │
└─────────┬─────────┘                                        └─────────┬─────────┘
          │                                                            │
   ① ─────▼──────────────────────────────────  ① ─────────────────────▼──────────
   detectNameModel   名称是否像一个型号         suggestSpec   生成规范写法（不自动写入）
     │  "NXB-63" 当名称 → 提示                    │  全角→半角 → 字符统一(∅→Φ)
     ▼                                           │  → 空格整理 → 单位大小写(mm2→mm^2)
   ② matchExcludeHint  边界词（业务规则）         │  → 多项式按"极数→电流"排序
     │  "电源线" @ 110303 → 不属于本小类          ▼
     ▼                                          ② fixSpecFormat  空格/全角整理结果
   ③ matchSystemWord   泛称（上位词）              │  与建议写法比对，算出 changes
     │  "门禁" → 请写具体：门禁控制器/读卡器…      ▼
     ▼                                          ③ symbolIssues   字符集问题
   ④ suggestName       同义词字典归一              │  must：CP936 变问号/降级（∅ º Ω）
     │  "监控硬盘"→"硬盘"、"超五类"→"超五类网线"    │  should：同义混用（φ ￠ Ф ∨ ㎜ ㎡）
     ▼                                           └────────────────────────────────
   ⑤ detectSubMismatch 名称 ↔ 小类一致性（7 层，见下）
     │  "膨胀管" @ 100105 → 更像 120405 其它
     └──────────────────────────────────────────────────────────────
```

### detectSubMismatch 的 7 层判定（由宽到严，命中即返回）

```
输入：名称 + 当前小类
  │
  ├─(1) 排除词：壳体/配件/支架/箱/钳/光缆组件… ──► 不判（是别的物）
  │
  ├─(2) 当前小类标准名被名称包含（"固定断路器"含"断路器"）──► 不判
  │
  ├─(3) 双归属豁免：当前类条数 ≥ 主导类 20% ──► 不判
  │       例「热缩管」101706 与 110404 各 120 条，两边都合法
  │
  ├─(4) 存量主导（name-sub-index.index）：
  │       某小类 ≥2 条且占该名称 ≥80% ──► 命中
  │       count ≥3 → error（红+阻断）；count =2 → warn（琥珀）
  │       例「电缆」802 条 @110302
  │
  ├─(5) 本小类无先例（name-sub-index.dist）：
  │       当前小类 0 条，别处 ≥2 条 ──► warn
  │       例「电源线」@100105 无先例，存量在 101604 插头(3)/110302 电缆(2)
  │
  ├─(6) 结构参照（guide-units.allUnitNames，仅 crossSub:true 的单元名）：
  │       名称 = 别的小类单元名/标准名 ──► error
  │       例「电话线」@110301 → 110303 电话线
  │
  └─(7) Dice 双字元相似度兜底：
          ≥0.9 → error；0.6~0.9 且领先当前类 0.25 → warn
```

## 四、规格分段补全的运行机制

```
用户输入 "NXB-63 3P C1"
        │
        ▼
┌────────────────────────────────────────────────────────────────┐
│ spec-complete.complete(sub, q, items)                          │
│                                                                │
│ ① patternSegments(sub)   读 naming-guide.specPattern 拆段：     │
│      {型号} {极数} {脱扣特性}{额定电流}A {分断能力} {额定电压}    │
│                            ↓ alias 翻译（guide-field-map）      │
│      型号 / 极数 / 脱扣曲线+额定电流 / 分断能力 / 额定电压        │
│      · 相邻占位符合并成段，保留分隔符（{芯数}*{截面} → 3*2.5）    │
│      · 参数库对不上的段（设备类型/关键参数/端头类型）直接跳过      │
│                                                                │
│ ② statOf(sub)            遍历该小类存量规格，用 extractParams   │
│                          统计每段的取值频次（5 分钟缓存）         │
│                                                                │
│ ③ 定位当前段：                                                  │
│      head 已填完的段之后 → 找末尾片段归属 → 否则取下一个未填段     │
│      （避免「型号」宽正则把 3P / C1 吞成型号）                    │
│                                                                │
│ ④ 出候选：前缀过滤 → 频次排序 → 单参数段补单位（10k → 10kΩ）      │
└────────────────────────────────────────────────────────────────┘
        │
        ▼
  前端渲染：灰字续写（看板）/ 候选条（插件）
  Tab 接受首个 · Alt+1~8 精确选 · 点击采用 · Esc 关闭
```

## 七、数据产物与依赖关系

```
materials.ndjson ──┬──► dedup ──► dedup-exact.json（一物多号候选簇）
（基线，23,059）    │              dedup-sep.json（仅分隔符差异）
                   │              dedup-sameNumber.json（一号多物）
                   │              name-sub-index.json ◄── 供 detectSubMismatch 第 4/5 层
                   │
                   └──► validate ──► extract-validation.json（黄金样例/契约/覆盖率）

materials-merged.ndjson ──► plm-index.loadIndex() ──► 内存索引
（当前生效源，23,406）                │                 ├─ items（物料）
                                     │                 ├─ bySig（签名）
                                     │                 └─ byLoose（弱签名）
```

**要点**：`name-sub-index.json` 是唯一"跨批处理与服务"的产物——`dedup` 生成，`material-rules` 5 秒缓存热读。

## 九、当前边界（已知缺口）

| 缺口 | 原因 | 影响 |
|---|---|---|
| 名称→小类判定对"库里散乱的新名称"无解 | 全库 5962 名称中 79% 频次 <3，无主导归属 | 只能靠 `excludeHints` 业务词表补 |
| 规格模板中 `设备类型/关键参数/端头类型/螺栓孔径/接线方式/连接容量` 无补全 | 参数库无对应参数（属那 209 个待补参数） | 这些段不弹候选 |
| 209 个小类里只有 3 个建了 `nameUnits` | 人工梳理成本 | 其余小类只能靠存量索引与 Dice |
| 「其它」类（101808 947 条 / 120405 2129 条） | 兜底分类 | 交叉验证出 477 条疑似错类，需人工治理 |
| 插件端无灰字续写 | 平台控件为原生 input，叠加层跟随重绘风险高 | 仅候选条 + Tab |

## 十、一句话总览

> **三条链路、一个编排器、九类配置、七个判定层。**
> 录入走 `checkMaterial`（名称 5 道 → 规格 3 道）与 `spec-complete`（模板分段 → 存量频次）；
> 批处理走 `extract → dedup → validate`，其中 `dedup` 产出的名称索引是录入判定的数据基础；
> 插件负责把 PLM 数据带回（快照），看板负责人工复核与规则维护，两者共用同一套规则引擎。
